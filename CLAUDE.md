# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`ToDo/` is a single-page to-do list app: plain HTML/CSS/JS, no build tools, no package manager, no framework. There is no dev server, bundler, linter, or test suite — the app is opened directly as a file in a browser.

- `ToDo/index.html` — page structure and the add-task form (text, due date, priority)
- `ToDo/style.css` — all styling, including light/dark theme via CSS custom properties
- `ToDo/app.js` — all application logic
- `ToDo/specs.md` — the running spec/requirements for the app; keep it in sync when features change
- `ToDo/test.html` — a **self-contained snapshot** of the app (HTML/CSS/JS all inlined in one file) used for manual testing in isolation. It is not auto-generated — if you change `index.html`/`style.css`/`app.js`, update `test.html` to match by hand if it needs to stay current.
- `ToDo/SECURITY_FIXES.md` — record of a past security pass (input validation, localStorage parsing, CSP); read it before touching validation logic so fixes aren't accidentally reverted.

## Running / verifying changes

Open `ToDo/index.html` directly in a browser (double-click, or `start ToDo/index.html` on Windows). There is no build step. Verify changes manually by exercising the UI (add/edit/delete/filter/search tasks, toggle theme, reload to confirm localStorage persistence).

## Architecture

All state lives in a single in-memory `tasks` array inside `app.js`, persisted to `localStorage` (key `todo-tasks`) on every mutation via `saveTasks()`/`loadTasks()`. There is no framework or virtual DOM: every mutation (`addTask`, `toggleTask`, `deleteTask`, `editTask`, `clearCompleted`) calls `saveTasks()` then `render()`, which wipes and rebuilds `#task-list` from scratch (`list.innerHTML = ""` + rebuild).

Each task object: `{ id, text, done, priority, dueDate }`.

- `id` — generated by `generateId()` (timestamp + random suffix), not just an incrementing counter, to avoid collisions/predictability.
- `priority` — one of `VALID_PRIORITIES = ["low", "medium", "high"]`; enforced both on add/edit and when loading from localStorage.
- Task validation (`isValidTask`) filters out malformed/corrupted entries when reading from `localStorage`, so a bad value there can't crash the app — it's silently dropped.

Display order and visibility are computed (not stored): `getVisibleTasks()` filters by the current `filter` (`all`/`active`/`completed`) and `searchQuery` (case-insensitive substring match on `text`), then sorts by due-date urgency (overdue → today → upcoming → none) and, within that, by `priority`. `render()` always calls `getVisibleTasks()` — it never mutates or reorders the underlying `tasks` array.

Theme (light/dark) is independent of task state: applied via `data-theme="dark"` on `<html>`, driven by CSS custom properties in `style.css`, and persisted separately under the `todo-theme` localStorage key. It defaults to `prefers-color-scheme` when nothing is saved yet.

Inline editing (`startEditing`) swaps a task's `<span class="text">` for a temporary `<input>` in place; saving/canceling is handled via `blur`/`Enter`/`Escape` and always ends by re-running `render()`.

## Conventions

- Input validation constants (`MAX_TASK_LENGTH`, `MAX_TASKS`, `VALID_PRIORITIES`) live at the top of `app.js` — reuse them rather than hardcoding limits elsewhere.
- User-facing text is inserted via `textContent`, never `innerHTML`, to avoid XSS; keep new rendering code consistent with this.
- `index.html` sets a `Content-Security-Policy` meta tag (`script-src 'self'`) — don't introduce inline `<script>` blocks or external script/style hosts in `index.html` without updating that policy (note `test.html` is the exception, since it's the inlined-everything test snapshot).
